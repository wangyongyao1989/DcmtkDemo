# CT 预处理管线优化总结：Data610/Data622 效果差异分析与应对

本说明文档针对 `Data610.bin` 与 `Data622.raw` 在原有预处理流程下显示效果差距巨大的问题，详细总结了修改原因、应对策略及底层原理。

---

## 1. 核心问题分析 (Gap Analysis)

通过对两个原始文件的流分析及处理结果对比，发现效果差异主要源于以下三个维度的失控：

### 1.1 物理含义缺失的“全局拉伸”
*   **原逻辑**：使用 `cv::minMaxLoc` 获取全图最大/最小值进行线性归一化。
*   **问题**：CT 图像背景通常包含大量空气（-1000 HU）及扫描床，或者存在个别极高亮的伪影（Hot Pixels）。这些极值会占据直方图的两端，导致中间真正关键的组织（如肺部、软组织）被挤压在极窄的灰度区间内，对比度严重丧失。

### 1.2 字节序与符号位的隐性冲突
*   **原逻辑**：硬编码大端序转换，默认有符号 16 位。
*   **问题**：不同厂家（GE vs Siemens）或不同存储格式（Raw vs DICOM Export）对字节序（Endianness）和像素表示（Pixel Representation）定义不同。一旦读取错误，像素值会发生大规模翻转，导致 HU 校正后的数据超出截断阈值，呈现全黑或全白。

### 1.3 噪声对调窗算法的干扰
*   **原逻辑**：对全图进行直方图统计。
*   **问题**：空气背景产生的低频噪声会误导自适应调窗算法，使其将重心偏移向背景区，而非人体组织区。

---

## 2. 应对策略与原理 (Strategies & Principles)

针对上述问题，我们对 `MedicalCTPreprocess.cpp` 中的 `CTFullPipeline` 进行了深度重构，引入了以下工业级策略：

### 2.1 引入人体组织 ROI 提取 (ROI-Based Processing)
*   **原理**：在统计直方图之前，先利用阈值分割（-600 HU）结合连通域分析，识别出人体主干区域（Body ROI）。
*   **改进**：后续的所有去噪、重采样及调窗统计均只在 ROI 区域内进行，彻底排除了空气背景和扫描床的干扰。

### 2.2 百分位百分比截断 (Percentile-Based Normalization)
*   **原理**：放弃全局 Min/Max，改用 **0.5% ~ 99.5% 分位数**。
*   **改进**：自动忽略掉直方图两端极少数的异常噪点或伪影。原理类似于临床上的“稳健统计”，确保 99% 的核心组织数据获得最大动态范围表现，大幅提升了图像的视觉鲁棒性。

### 2.3 启发式字节序校验 (Heuristic Endianness Check)
*   **原理**：在 `LoadRawPixelBuffer` 中增加了极值监控逻辑。
*   **改进**：如果以当前设定的字节序读取出超出物理常识的 HU 值（如 > 30000），系统会在日志中发出警告并提示开发者检查 Endianness 设置。

### 2.4 临床标准窗位兜底 (Standard Window Fallback)
*   **原理**：自适应算法虽然灵活，但在极端数据（全损、全黑）下可能失效。
*   **改进**：增加了窗宽检测逻辑。如果计算出的窗宽（W）小于 100 HU（说明数据分布极其异常），则自动退化为临床标准的 **软组织窗 (WindowCenter=40, WindowWidth=400)**，保证基本的可视化需求。

---

## 3. 修改后的 Pipeline 流程对比

| 阶段 | 旧流程 (Standard) | 新流程 (Enhanced) | 解决的核心痛点 |
| :--- | :--- | :--- | :--- |
| **载入** | 直接载入 | 载入 + 极值启发式校验 | 字节序错误预警 |
| **定位** | 全图处理 | **自动 Body ROI 提取** | 排除空气/扫描床干扰 |
| **统计** | `minMaxLoc` | **0.5%-99.5% 分位数统计** | 抑制噪点/伪影对对比度的挤压 |
| **映射** | 线性归一化 | **自适应调窗 + 临床标准兜底** | 保证诊断关注区的视觉效果 |
| **增强** | 基础 CLAHE | 优化参数的 CLAHE | 抑制局部噪声放大 |

---

## 4. 结论与建议

经过上述优化，`Data610.bin` 和 `Data622.raw` 即使在源格式存在微小差异的情况下，也能通过“自动 ROI -> 百分位调窗”这一链路获得一致且高质量的视觉输出。

**建议**：在后续开发中，建议将 `Data622.raw` 的具体元数据（如确切的存储字节序）写入配置文件，由 UI 端动态传参，以替代当前的启发式猜测，从而达到 100% 的解析准确率。
